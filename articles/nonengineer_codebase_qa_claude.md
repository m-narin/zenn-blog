## はじめに

社内向けに、**非エンジニアでも「対象リポジトリの実装をもとに」仕様や要件を調査できるツール**を作りました。本記事ではこれを仮に 社内 Claude Codeと呼びます。

ざっくり言うと、

> 「この機能って今どういう挙動になってる？」「この条件のとき何が起こる？」
> をビジネス職の人がブラウザのチャットから聞くと、**実際のコードを読んだうえで**平易な日本語で答えてくれる

というものです。裏側では [Claude Code](https://docs.claude.com/en/docs/claude-code) をエージェントとして動かしています。

## 背景：仕様の「正解」はコードにしかない

プロダクトが育つと、ドキュメントは必ず実装から遅れます。「仕様書にはこう書いてあるけど、実際のコードは違う」はあるあるです。結局、**いま動いている挙動の正解はコードにしかない**。

ところがコードを読めるのはエンジニアだけ。そのため、ビジネス職やデザイナーが仕様を確認したいとき、こういう流れになりがちです。

1. Biz「この場合どうなるんでしたっけ？」
2. エンジニアに Slack で確認依頼
3. エンジニアが手を止めてコードを読み、回答
4. （回答が来るまで Biz 側の議論は止まる）

この **「エンジニアを経由しないと実装ベースの事実が分からない」** という構造が、地味だけど確実にボトルネックになっていました。

- Biz 側は、エンジニアの手が空くまで議論を進められない
- エンジニア側は、調査依頼で細切れに集中を奪われる

## 目的：エンジニアを介さずに「実装ベースの一次情報」へ到達する

なので狙いはシンプルで、**ビジネス職が自分でコードベースに質問できる状態を作る**ことです。

ポイントは「それっぽい一般論」ではなく、**対象リポジトリの実際のコードを根拠に答える**こと。RAG で関連ドキュメントを拾うのではなく、エージェントに実際のソースを `grep` / `read` させて、事実をもとに回答させます。

これによって、

- Biz は、エンジニアを待たずに仕様前提を確認して議論を前に進められる
- エンジニアは、定型的な「これどうなってる？」調査から解放される

という、**議論の初速** を上げるのが一番のバリューです。エンジニアへのエスカレーションを「ゼロ」にするのが目的ではなく、**その手前で済むものを済ませる**のが狙いです。

## 全体構成（ざっくり）

構成はかなり素朴です。凝ったインフラは使っていません。

```
ブラウザ (チャットUI)
   │  HTTPS / SSE でストリーミング
   ▼
APIサーバー（常駐プロセス）
   │  質問ごとに Claude CLI を1プロセス起動
   ▼
Claude Code (claude -p --output-format stream-json)
   │  対象リポジトリを read-only で調査
   ▼
ローカルにcloneした対象リポジトリ群（定期 git pull で最新化）
```

- **フロント**: チャット UI。回答はストリーミング表示。
- **バックエンド**: 常駐の API サーバー。ユーザーが質問を送るたびに **Claude CLI を 1 セッション = 1 プロセスとして spawn** する。
- **エージェント**: Claude Code。対象リポジトリのコードを読んで回答する。
- **対象リポジトリ**: サーバー上に clone しておき、**定期的に `git pull --ff-only`** して最新の実装に追従させる（後述）。
- **認証**: 社員だけがアクセスできればよいので、IdP（Identity-Aware Proxy 的なもの）でアクセス制御。
- **データ**: チャット履歴などはファイルベースの軽量 DB（SQLite）で十分。

「LLM プロダクト」と聞くと大げさな構成を想像しがちですが、**本質は「Claude Code を Web から叩けるようにしただけ」** です。GUI ラッパーに近い。

## 対象リポジトリを「どう読んでいるか」と権限設計

ここが一番気になるところだと思います。「社内のソースコードを AI に読ませる」「非エンジニアが触る」と聞くと、まず**権限・セキュリティ**が心配になるはずです。整理して書きます。

### どうやってコードを読んでいるのか

仕組み自体は拍子抜けするほど素朴で、**サーバー上に対象リポジトリを `git clone` しておき、Claude CLI をそのディレクトリで起動するだけ** です。

```
/repos/
  ├── service-a/   ← git clone 済み（定期 pull で最新化）
  ├── service-b/
  └── ...
```

CLI 起動時に `cwd`（作業ディレクトリ）をそのリポジトリに向けます。

```ts
const proc = Bun.spawn(["claude", ...args], {
  cwd: "/repos/service-a", // ← ここを起点に Claude がファイルを読む
  // ...
});
```

あとは **Claude Code 標準のファイル読み取り能力**（Read / Grep / Glob や、`grep` `cat` `find` といった読み取り系シェルコマンド）で、人間のエンジニアがやるのと同じようにファイルを開いて検索します。**事前にコードをベクトル化したりインデックスを張ったりはしていません**。エージェントがその場でファイルシステムを読みに行く、という素直な作りです。これが「ドキュメントの孫引きではなく、コードという一次情報で答えられる」理由でもあります。

### 権限は「2 つの軸」で考える

権限の話は、混ざると分かりにくいので 2 軸に分けて考えました。

1. **アクセス制御（誰がこのツールを使えるか）**
2. **書き込み制御（AI が何かを壊さないか）**

### 軸1: 誰が使えるか — 入口で社員に限定する

そもそも社外の人に使われては困るので、**入口で認証**します。ここでは IdP（Identity-Aware Proxy 的なもの）を前段に置き、Google アカウントでログインした社員だけがアプリに到達できるようにしています。アプリ側は、IdP が付与する認証済みメールのヘッダを信頼してユーザーを識別します。

```ts
// 本番は IdP が付ける認証済みメールのヘッダを見るだけ
const iapHeader = c.req.header("X-Goog-Authenticated-User-Email");
const email = iapHeader?.split(":").pop() ?? null;
if (!email) return c.json({ error: "Authentication required" }, 401);
// さらに DB 上で「有効化済みユーザー」だけを通す
```

さらにアプリ内でも DB のユーザー管理で「有効化された人だけ」に絞り、**どのリポジトリを選べるか** も管理者が制御できます。つまり「**ネットワーク的な入口（IdP）**」と「**アプリ内の権限（有効ユーザー・公開リポジトリ）**」の二重で、見せる相手と見せる範囲をコントロールしています。

### 軸2: 何も壊さないか — read-only を多層で担保する

非エンジニアが触る以上、「**絶対に何も壊さない**」と言い切れることが導入の前提でした。これは 1 つの仕組みに頼らず、**多層**で担保しています。

1. **プロンプトで禁止する**（前述）。ファイルの作成・編集・削除、`sed -i` `rm` `mv` 等の破壊的コマンドを禁止し、読み取り系コマンドのみ許可。
2. **そもそも書き戻せないようにする**。サーバーには**リポジトリへ push できる書き込み権限（write 権の認証情報）を置きません**。コードの取得は読み取り専用の clone と `pull --ff-only` だけ。仮にエージェントがローカルで何か書こうとしても、**リモート（GitHub 等）には反映されない**。ローカルの変更も次回 pull で巻き戻りますし、必要なら専用ユーザー＋読み取り専用マウントで OS レベルに固めることもできます。
3. **スコープを限定する**（前述）。読める範囲を対象ディレクトリに絞る。

:::message alert
正直に書くと、`--dangerously-skip-permissions` を付けて Claude Code の確認プロンプトを無効化しています。非エンジニア向けに「実行してよいですか？」を毎回出すと使い物にならないためです。その代わり、**「破壊的操作はプロンプトで禁止」＋「書き込み資格情報を環境に置かない」＋「最新コードは pull で常に上書きされる」** という多層で安全側に倒しています。`--dangerously-skip-permissions` は強力なフラグなので、採用するなら「**書き込み権限を渡さない実行環境**」とセットにするのが肝心です。
:::

### サーバーが Git リポジトリを読むための権限

「サーバーがどんな権限でプライベートリポジトリを clone / pull しているのか」も気になるところだと思います。ここは **「OS ユーザーの権限」と「GitHub への認証」の 2 段** で考えると整理しやすいです。

**① OS は専用の低権限ユーザーで動かす**

`root` ではなく、専用ユーザー（例: `deploy`）を作り、アプリも `git pull` も Claude CLI も**すべてそのユーザーとして実行**します。

- `deploy` がアプリ用ディレクトリと `/repos` を所有する
- `deploy` に与える `sudo` は **自分のサービスの再起動（`systemctl restart ...`）程度に限定**し、それ以外の root 権限は持たせない
- `git config --global --add safe.directory '*'` で `/repos` 配下を git 操作できるようにしておく

**② GitHub への認証は SSH 鍵で、秘密鍵はサーバーから出さない**

プライベートリポジトリを取得するには GitHub への認証が要ります。サーバー上で SSH 鍵を生成し、**公開鍵だけ**を GitHub に登録します。秘密鍵はサーバーの中に置いたまま外に出しません。

```bash
# サーバー上で鍵を生成し、公開鍵だけを GitHub に登録する
ssh-keygen -t ed25519 -C "code-qa-server" -N "" -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub   # ← これを GitHub 側に登録
```

**③ 鍵は「read-only」にして、push できないことを保証する**

ここが権限設計の肝です。理想は **リポジトリ単位の read-only な Deploy Key** を使うこと。

- GitHub の **Deploy Key（リポジトリ単位）を read-only で登録**すれば、その鍵では **clone / pull はできても push は不可能**になる。
- これで「**サーバーには書き込み権限を置かない**」が、運用ルールではなく**鍵レベルで保証**されます。先に述べた read-only 多層防御の、一番下の土台がこれです。

| レイヤ | 何で守るか |
|---|---|
| OS | 専用ユーザー（root でない／sudo は自サービス再起動のみ） |
| GitHub 認証 | サーバー生成の SSH 鍵（秘密鍵は外に出さず、公開鍵だけ登録） |
| 読み取り専用 | **リポジトリ単位の read-only Deploy Key** → push 不能を鍵で担保 |

:::message
アカウント全体の SSH 鍵を 1 つ登録して使い回すこともできますが、それだとその鍵で**書き込みも技術的に可能**になってしまいます。「読むためだけ」と言い切るために、**対象リポジトリごとに read-only の Deploy Key を発行する**のがおすすめです。
:::

### 秘密情報の扱い

コードを読ませる以上、**読ませてよいものだけを置く**のが大原則です。`.env` や鍵などの秘密情報はリポジトリに含めない（含まれないよう運用する）、対象リポジトリは公開してよい範囲に絞る、といった前提のうえで成り立っています。「AI に社内コードを読ませる」こと自体より、**そのコードに秘密が混ざっていないか**のほうが実務上のリスクなので、ここは普段のリポジトリ運用の延長で気をつける、という整理にしています。

## 技術的な実現方法とコツ

### 1. 質問ごとに Claude CLI を non-interactive で起動する

エージェント本体は Claude Code の CLI をそのまま使います。Web からの 1 リクエスト = CLI の 1 実行です。バックエンド（今回は Bun）から、おおよそ次のように起動します。

```ts
// 質問が来るたびに Claude CLI を 1 プロセス起動する（イメージ）
const args = [
  "-p",                                  // print / non-interactive（ワンショット）
  "--output-format", "stream-json",      // トークンを逐次受け取る
  "--verbose",
  "--model", model,
  "--append-system-prompt", systemPrompt, // 役割・制約を毎回注入
  "--mcp-config", mcpConfigPath,
  "--strict-mcp-config",                  // 繋ぐ MCP を明示的に限定
  "--dangerously-skip-permissions",       // 調査専用なので権限プロンプトは出さない
];

const proc = Bun.spawn(["claude", ...args], {
  cwd: repoPath,        // ← 調査対象リポジトリを作業ディレクトリにする
  stdin: promptStream,  // 質問文を stdin で渡す（引数長制限の回避）
  env: cleanEnv,        // ← 後述: 起動元の Claude 由来 env を消しておく
});
```

`--output-format stream-json` で 1 行 1 JSON イベントが流れてくるので、それをパースしてそのまま SSE でフロントへ中継すれば、ChatGPT 風の逐次表示になります。

```ts
// stdout を行ごとに読んで、assistant の差分テキストだけ SSE で流す
for await (const line of readLines(proc.stdout)) {
  const ev = JSON.parse(line);
  if (ev.type === "assistant") {
    for (const block of ev.message.content) {
      if (block.type === "text") sse.send({ type: "delta", text: block.text });
    }
  }
}
```

:::message
ハマりどころとして、ランタイムによっては子プロセスの標準出力パイプが早期に閉じることがありました。対策として **stdout を一時ファイルにリダイレクトし、それをポーリングで読む** 方式に逃がしています。また、サーバー自体を Claude Code 上で開発していると、起動元の環境変数が子プロセスに継承されて干渉します。spawn 前に消しておくと安定します。

```ts
const cleanEnv = { ...process.env };
delete cleanEnv.CLAUDECODE;             // ネスト実行の検出回避
delete cleanEnv.CLAUDE_CODE_ENTRYPOINT;
```
:::

### 2. システムプロンプトで「役割」と「安全性」を固める

非エンジニア向けツールなので、プロンプトで人格と制約を強めに定義します。`--append-system-prompt` に渡す中身は、たとえばこんな雰囲気です。

```ts
const systemPrompt = `あなたはコードベースに精通したシニアエンジニアとして質問に答えるアシスタントです。
利用者は主に非エンジニア（ビジネス職・デザイナー等）です。専門用語を避け、平易な日本語で答えてください。
コードスニペットは原則貼らず、わかりやすい言葉で説明すること。

## 回答の原則
- 推測で答えない。必ずコードを読んで根拠（ファイルパス）を確認してから断定する。
- わからない場合は正直に「わからない」と言う。

## 制約（最重要）
- 閲覧・検索・分析は自由。ただしファイルの作成・編集・削除は絶対に行わない。
- 破壊的な Bash（echo >, sed -i, mv, rm, cp, touch, mkdir 等）は使用禁止。
- 使ってよいのは読み取り系コマンド（grep, ls, cat, find, git log, git diff 等）のみ。
`;
```

「`--dangerously-skip-permissions` で権限を外す」かわりに、**プロンプトとコマンド方針で read-only を担保する**、という発想です。

### 3. 調査スコープを限定する

リポジトリ全体を毎回フルスキャンさせると、遅いし的外れな回答も増えます。そこで **「対象範囲（ディレクトリ群）」を選べる** ようにし、システムプロンプトに追記して強制します。

```ts
const scopeInstruction = `
## 対象範囲（必ず遵守）
このセッションのスコープは以下のディレクトリに厳密に限定されます。
${paths.map((p) => `- ${p}`).join("\n")}

- 調査・回答はすべて上記ディレクトリ内に限定する。
- 範囲外の質問には調査せず「対象範囲外です」と即答する。
- grep / find は対象ディレクトリをルートに実行する。
`;
```

スコープを切るだけで、回答速度と精度の両方が目に見えて改善します。

### 4. 「UI 用語 ↔ コード上の名前」の用語辞書を注入する

非エンジニアは当然 **UI 上の言葉** で質問してきます（例:「"お気に入り" の上限は？」）。一方コード上の名前は別物（例: `favorites` テーブル）です。このギャップを埋めるため、リポジトリごとに **用語辞書（UI 用語 ⇔ DB / コード名の対応表）** を Markdown で持っておき、システムプロンプトに注入します。

```ts
// data/glossaries/{repositoryId}.md を読んでプロンプトに足すだけ
const glossary = readGlossaryForRepo(repositoryId); // 例: "お気に入り → favorites テーブル"
const glossaryInstruction = glossary
  ? `\n## 用語辞書（常に参照）\nUI 用語で聞かれたら下表で DB/コード名に翻訳して調査し、回答時は両方を併記すること。\n\n${glossary}`
  : "";
```

これで「ユーザーの言葉 → コード名に翻訳して調査 → 回答は両方を併記」という動きになり、質問の解釈ミスが激減します。**ドメイン知識の最後のすり合わせを、辞書という軽量な仕組みで効かせる** のがポイントです。

### 5. フィードバックを次の回答に効かせる（簡易 RAG）

回答に Biz が「良い / 悪い」を付けられるようにし、**高評価だった「質問 ↔ 回答」を蓄積** します。新しい質問が来たら、同じリポジトリの過去フィードバックから似た質問を拾い、「参考回答」としてプロンプトに差し込みます。

最初の実装は文字 n-gram の一致率という素朴なものです。これで十分効きました。

```ts
// 2-gram の集合一致率（Jaccard）でゆるく類似質問を引く
function similarity(a: string, b: string): number {
  const grams = (s: string) =>
    new Set(Array.from({ length: Math.max(0, s.length - 1) }, (_, i) => s.slice(i, i + 2)));
  const A = grams(a), B = grams(b);
  const inter = [...A].filter((g) => B.has(g)).length;
  return inter / (A.size + B.size - inter || 1);
}
// 高評価フィードバックを類似度でソートして上位 N 件だけプロンプトへ
```

将来はベクトル検索に差し替え可能な作りにしておく、くらいの温度感で十分でした。

### 6. MCP は「必要な分だけ」自作する

Claude Code は MCP サーバーを繋げられます。とはいえ大層なものは要らず、**チャットのタイトルを会話内容から自動更新する** ような小さなツールを 1 つ自作して繋いでいる程度です。

```ts
// 自作 MCP サーバー（stdio）の例：タイトル更新ツールを 1 つだけ公開
const server = new McpServer({ name: "cloud-claude-code", version: "1.0.0" });

server.tool(
  "update_session_title",
  "Update the current chat session title",
  { title: z.string().describe("New session title (max 20 chars)") },
  async ({ title }) => {
    db.prepare("UPDATE chat_threads SET title = ? WHERE id = ?").run(title, SESSION_ID);
    return { content: [{ type: "text", text: `updated: ${title}` }] };
  },
);
```

`--strict-mcp-config` で繋ぐ MCP を絞り、**標準のファイル読み取り能力を主役にして、足りない細部だけ MCP で足す** くらいがちょうどよかったです。

### 7. 対象リポジトリは定期 pull で鮮度を保つ

回答の正しさは **コードの鮮度** に直結します。古いコードを読んで「現在の仕様です」と答えてしまっては本末転倒なので、調査対象リポジトリは常に最新へ追従させます。流れはこうです。

```
① 初回: サーバーの /repos 配下に対象リポジトリを git clone（最初の取り込み）

② 以降の更新は systemd timer で定期キック
   pull-repos.timer    ← 定期トリガー（cron 相当）
        │ 起動
        ▼
   pull-repos.service  ← 実行ユニット
        │ 実行
        ▼
   bin/pull-repos      ← /repos/*/ を順番に git pull --ff-only
        ▼
   /repos/service-a, /repos/service-b ...  ← 常に最新コードに保たれる
        ▲
        └─ Claude はここを cwd にして読みに行く（= 常に最新を読む）
```

つまり「**アプリ本体（このツールのコード）**」と「**調査対象のコード（/repos 配下）**」は別管理で、後者は **ランタイム上で `pull-repos` が最新化し続ける** 形です。調査対象のソースはアプリのリポジトリには含めず（`.gitignore` 対象）、サーバー上にだけ存在します。

肝心の `bin/pull-repos` 自体は、素朴なシェルスクリプトで十分です。

```bash
#!/bin/bash
# /repos 配下のリポジトリを定期的に最新化する（pull-repos.timer から呼ばれる）
for repo in /repos/*/; do
  [ -d "${repo}.git" ] || continue
  # （必要なら）DB に登録されたデフォルトブランチへ checkout してから pull する
  git -C "$repo" pull --ff-only || echo "WARN: pull failed for $repo"
done
```

systemd 側は timer と service の 2 ファイルだけ。たとえば「15 分ごとに pull する」ならこんなイメージです。

```ini
# pull-repos.timer
[Timer]
OnBootSec=5min
OnUnitActiveSec=15min   # 前回実行から 15 分ごと

[Install]
WantedBy=timers.target
```

```ini
# pull-repos.service
[Service]
Type=oneshot
ExecStart=/opt/cloud-claude-code/bin/pull-repos
```

`--ff-only` にしているのは、**ローカルでの予期しない変更とコンフリクトさせず、リモートの履歴をそのまま早送りで取り込む**ためです（前述のとおりサーバーには書き込み権限を置かないので、ローカルが汚れる前提でもありませんが、安全側に倒しています）。この「定期 pull」によって、Biz が今この瞬間に質問しても **直近のコードに基づいた回答** が返る、という鮮度が担保されます。

## コアな価値：どこに効くのか

技術的には「Claude Code の Web ラッパー」ですが、価値の本質はそこではありません。

### ① エンジニアを経由しない「実装の一次情報」アクセス

これまで **エンジニアという人間 API** を叩かないと得られなかった「実装ベースの事実」を、Biz が直接取りに行けるようになりました。重要なのは、回答が **ドキュメントの孫引きではなくコードという一次情報** に基づくこと。だから「ドキュメントが古くて違った」が起きにくい。

### ② 議論の初速が上がる

一番効くのはここです。Biz は「エンジニアの手が空くのを待つ」工程をスキップして、**仕様の前提を確認したうえで議論を始められる**。確認待ちで会議が止まる、という無駄が減ります。

### ③ エンジニアの集中を守る

「これどうなってます？」の定型調査がツールに吸われることで、エンジニアは細切れの割り込みから解放されます。**本当にエンジニアの判断が要る相談だけ** が人間に回ってくる、という良い切り分けになります。

### ④ 心理的な安全弁としての read-only

非エンジニアが触るからこそ、**「絶対に何も壊さない（read-only）」** であることが導入のしやすさに直結しました。「コードを読むだけ」と言い切れると、対象リポジトリを広げる際の合意も取りやすい。

## まとめ

- 仕様の正解は結局コードにあるが、これまでそこへ到達できるのはエンジニアだけだった。
- **Claude Code を Web から叩けるようにし、非エンジニアが実装ベースで質問できる** ようにしたのが ccc。
- 技術的には素朴（CLI を spawn + ストリーミング + read-only プロンプト + スコープ限定 + 用語辞書 + 簡易フィードバック）。
- 価値の本質は **「エンジニアを介さず実装の一次情報に到達でき、議論の初速が上がる」** こと。

「AI に社内のコードを読ませて Biz の質問に答えさせる」というアイデア自体は、どの会社でも応用が効くはずです。凝ったものを作る前に、**まず CLI を Web から叩くだけ** から始めるのがおすすめです。
