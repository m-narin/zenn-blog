## はじめに

プロジェクトが育ってくると、CI の実行時間はじわじわと伸びていきます。テストが増え、ビルド対象が増え、気づけば「PR を出してから緑になるまで 20 分待つ」みたいな状態になりがちです。CI が遅いと、

- マージまでのリードタイムが伸びる
- 待ち時間にコンテキストスイッチが発生して集中が切れる
- GitHub Actions の従量課金がじわじわ効いてくる

と、地味だけど確実に開発体験とコストを蝕んできます。

この記事では、**実行時間を削るための工夫**をまとめて紹介します。GitHub Actions を前提にしていますが、考え方の多くは他の CI でも通用するはずです。

なお、ここで紹介する施策は **GitHub Actions の基礎概念（ワークフロー → ジョブ → ステップの 3 階層、トリガー、ランナー、reusable workflow / composite action など）を知っていると、「なぜそれで速くなるのか」がスッと腑に落ちます**。たとえば「ジョブは並列で走る／`needs` で直列になる」「ランナーは使い捨て（エフェメラル）だから毎回まっさらな環境になる＝だからキャッシュが要る」といった前提が分かっていると、後述のアイデアの効きどころが見えてきます。このあたりの土台が怪しい方は、先に基礎をさらっておくと読みやすいはずです。

- [【GitHub Actions】基礎とその可能性](https://qiita.com/MandoNarin/items/bb796b675c5a96ba04a3)

そして大前提として、**やみくもに手を付ける前に、まず計測してボトルネックを特定する**のが鉄則です。「遅い気がする」で並列数を増やしても、本当の原因が別のところ（特定の重いテスト 1 本、ビルドの非効率など）にあると、効果が出ません。なので本記事はまず計測の話から始め、そのうえで、計測で見つかったボトルネックに対して打つ施策を紹介していきます。

施策は大きく分けて次の 5 系統です。

1. **キャッシュを効かせる**（依存解決・ビルド・Lint）
2. **テストを並列化して、賢く分割する**
3. **そもそも動かさない**（変更パスでスキップ・重複実行のキャンセル）
4. **ランナーを使い分ける**（重い処理だけ強いマシン・アーキテクチャの選択）
5. **個々のジョブ自体を速くする**（テスト用 DB・ランタイム最適化）

まずは計測、それから順番に見ていきます。

## まず計測する：どこが遅いかを知る

高速化の出発点は、**「どこに時間がかかっているか」を数字で把握する**ことです。体感や思い込みで手を付けると、効果の薄いところに労力を使ったり、本当のボトルネックを見落としたりします。「計測 → ボトルネック特定 → そこに合った施策で対応」という順番を徹底するだけで、費用対効果が大きく変わります。

### ワークフロー全体のどのジョブが遅いか

GitHub Actions なら、まずは Actions の実行画面で各ジョブ・各ステップの所要時間を眺めるのが第一歩です。「test に 10 分、build に 5 分、lint は 30 秒」のように、**時間を食っている上位のジョブ**が見えてきます。クリティカルパス（一番長い依存の鎖）に乗っているジョブはどれか、という観点で見るのが大事です。並列で走っている軽いジョブをいくら速くしても、全体時間は縮みません。

### テストスイートの中のどこが遅いか

ジョブの中で一番ありがちなボトルネックがテストです。テストの中の「どこが遅いか」までブレイクダウンすると、打ち手が具体的になります。Rails / RSpec なら [`test-prof`](https://github.com/test-prof/test-prof) が定番です。テストスイートのプロファイラ集で、たとえば次のようなことが分かります。

- **どのテストファイル・example が遅いか**（実行時間ランキング）
- **factory（FactoryBot）でレコードを作りすぎていないか**（`FactoryProf`）
- **同じデータを毎回作り直していないか**（`let_it_be` / `before_all` で使い回せるか）
- **N+1 が起きていないか**（`EventProf` など）

```bash
# 例: factory の生成回数をプロファイルして「作りすぎ」を炙り出す
FPROF=1 bundle exec rspec

# 例: 各 example の実行時間を計測する（RSpec 標準のプロファイル出力）
bundle exec rspec --profile 20
```

### 計測結果をボトルネック対応につなげる

計測でボトルネックの当たりがついたら、その性質に合った施策を選びます。本記事の後半は、この「対応」のカタログだと思ってください。

- **依存インストール・ビルドが長い** → キャッシュを効かせる（1 章）
- **テスト全体が単純に量で重い** → 並列化して分散する（2 章）
- **触っていない領域のジョブまで走っている** → 変更パスでスキップ・重複実行をキャンセル（3 章）
- **重い処理が非力なランナーに張り付いている** → ランナーを使い分ける（4 章）
- **特定のテストや DB アクセスが遅い** → テスト自体・テスト用 DB を速くする（5 章）

ポイントは、**「並列化で N 分の 1 にする」前に「そもそも遅い 1 本を直す／使い回す」ほうが、効果も大きく副作用も少ないことがよくある**、ということです。計測で原因を絞ってから、対応の打ち手を選びましょう。

## 1. キャッシュを効かせる

CI 時間のうち、地味に大きいのが「依存関係のインストール」です。毎回ゼロから `bundle install` / `pnpm install` していると、それだけで数分溶けます。ここはキャッシュで潰すのが第一歩です。

### 依存パッケージのキャッシュ

最近の setup 系アクションは、ロックファイルをキーにしたキャッシュを内蔵しているので、まずはそれを使うのが一番ラクです。

Ruby なら `ruby/setup-ruby` の `bundler-cache`:

```yaml
- uses: ruby/setup-ruby@v1
  with:
    bundler-cache: true   # Gemfile.lock をキーに gem をキャッシュ
```

Node なら `actions/setup-node` の `cache`:

```yaml
- uses: actions/setup-node@v6
  with:
    node-version-file: .node-version
    cache: pnpm           # pnpm-lock.yaml をキーにキャッシュ
```

これだけで、ロックファイルが変わらない限り依存のインストールがほぼスキップされます。複数のワークフローで同じセットアップを使い回すなら、**composite action（`.github/actions/` 配下の `action.yml`）に切り出しておく**と、各ワークフローからは 1 行で呼べてメンテも一箇所で済みます。

### Lint 結果のキャッシュ

ESLint や RuboCop のような静的解析も、変更のないファイルまで毎回フル解析すると無駄です。ESLint は解析結果をキャッシュできるので、それを `actions/cache` で永続化しておくと差分だけの解析になります。

```yaml
- name: Cache ESLint results
  uses: actions/cache@v5
  with:
    path: node_modules/.cache/eslint
    key: eslint-${{ hashFiles('eslint.config.mjs', 'pnpm-lock.yaml') }}
    restore-keys: |
      eslint-
- run: pnpm lint --cache
```

ポイントは `restore-keys` を緩めに（プレフィックスだけで）置いておくこと。完全一致のキャッシュが無くても、直近のキャッシュを土台にして差分だけ解析できるので、キャッシュミス時の劣化がゆるやかになります。

### Docker ビルドのレイヤーキャッシュ

イメージをビルドして push するワークフローでは、Docker のレイヤーキャッシュが効果絶大です。`docker/build-push-action` で、レジストリ（コンテナレジストリ）にキャッシュ専用タグを置く構成にします。

```yaml
- uses: docker/setup-buildx-action@v4

- name: Build and push
  uses: docker/build-push-action@v7
  with:
    context: .
    push: true
    cache-from: type=registry,ref=${{ env.IMAGE_REPO }}:buildcache
    cache-to: type=registry,ref=${{ env.IMAGE_REPO }}:buildcache,mode=max
```

- `cache-from` で前回ビルドのキャッシュレイヤーを取得し、変わっていないレイヤーを再利用する
- `cache-to` の **`mode=max`** で、最終イメージだけでなく **マルチステージビルドの中間レイヤーまで**キャッシュする。これにより次回のキャッシュヒット率が上がる

GitHub Actions のキャッシュを使う `type=gha` という選択肢もありますが、`type=gha` には容量上限（リポジトリあたり数 GB）があり大きなイメージだとすぐ溢れます。レジストリを使える環境なら `type=registry` のほうが安定します。

#### キャッシュは「定期的に温め直す」

レイヤーキャッシュは便利ですが、**放っておくと古くなる**という弱点があります。ベースイメージのセキュリティ更新や OS パッケージの更新が、キャッシュに乗ったままだと取り込まれません。

そこで、**定期的にキャッシュをまるごと作り直す cron ワークフロー**を用意しておくと安心です。

```yaml
on:
  schedule:
    - cron: "0 19 * * 1"   # 週1回まとめてリフレッシュ

# ...
- uses: docker/build-push-action@v7
  with:
    context: .
    push: false
    no-cache: true          # キャッシュを無視してフルビルドし
    cache-to: type=registry,ref=${{ env.IMAGE_REPO }}:buildcache,mode=max  # 結果でキャッシュを上書き
```

普段の PR ビルドは差分だけで速く、週 1 でキャッシュを最新化する、という二段構えです。

## 2. テストを並列化して、賢く分割する

CI 時間の大半はだいたいテストです。ここを並列化できるかどうかで体感が大きく変わります。

### プロセス並列（1 ランナー内でコアを使い切る）

Rails の RSpec なら [`parallel_tests`](https://github.com/grosser/parallel_tests) で、1 つのランナー内の複数 CPU コアにテストを分散できます。マルチコアの大きめランナーを使うなら、まずこれでコアを使い切ります。

ただ素朴に分割すると、**グループごとの実行時間がバラついて、一番遅いグループに全体が引っ張られます**。これを解決するのが「実行時間ログ」です。

`parallel_tests` は各テストの実行時間を `tmp/parallel_runtime_rspec.log` に記録でき、**次回はそのログを見て、各グループの合計時間が均等になるように分割**してくれます。

```
# .rspec などに追加して実行時間を記録
--format ParallelTests::RSpec::RuntimeLogger --out tmp/parallel_runtime_rspec.log
```

CI ではこのログを**キャッシュして次回に引き継ぐ**のがコツです。

```yaml
- name: Restore runtime log cache
  uses: actions/cache/restore@v5
  with:
    path: tmp/parallel_runtime_rspec.log
    key: runtime-log-${{ runner.os }}-${{ hashFiles('spec/**/*_spec.rb') }}
    restore-keys: |
      runtime-log-${{ runner.os }}-
```

これで「過去の実行時間を学習して、グループ間の偏りを減らす」というフィードバックループが回ります。テストを足したり消したりしても、`restore-keys` のプレフィックス一致で直近のログを土台にできるので、いきなり偏ることはありません。

### シャーディング（複数ランナーに分散）

フロントエンドのテスト（Vitest / Jest など）は、**シャーディング**で複数ランナーに分散できます。GitHub Actions の matrix strategy と組み合わせるのが定番です。

```yaml
frontend-test:
  strategy:
    fail-fast: true
    matrix:
      shard: [1/2, 2/2]
  runs-on: ubuntu-latest
  steps:
    - run: pnpm vitest run --shard=${{ matrix.shard }}
```

`shard: [1/2, 2/2]` で「全体を 2 分割した 1 つ目／2 つ目」という指定になり、2 つのジョブが並列で走ります。テスト量が増えてきたら `[1/4, 2/4, 3/4, 4/4]` のように分割数を増やすだけでスケールします。

`fail-fast: true` を入れておくと、どこかのシャードが落ちた瞬間に残りもキャンセルされるので、無駄なランナー時間を使いません。

:::message
プロセス並列（`parallel_tests`）とシャーディング（matrix）は排他ではなく、**併用できます**。「matrix で N 台に分け、各台の中で parallel_tests がコアを使い切る」という二段並列にすると、さらに縮みます。
:::

## 3. そもそも動かさない

一番速い処理は「動かさない処理」です。実行時間を削るうえで、**走らせなくていいものを走らせない**のは最も効果が大きい施策です。

### 変更パスでジョブをスキップする

フロントエンドしか触っていない PR で、重いバックエンドテストをフルで回すのは無駄です。`dorny/paths-filter` を使うと、変更されたファイルのパターンを判定して、ジョブごとに走らせる／スキップを切り替えられます。

```yaml
jobs:
  check-diff:
    runs-on: ubuntu-latest
    outputs:
      backend_changed: ${{ steps.filter.outputs.backend }}
      frontend_changed: ${{ steps.filter.outputs.frontend }}
    steps:
      - uses: actions/checkout@v5
      - uses: dorny/paths-filter@v4
        id: filter
        with:
          filters: |
            backend:
              - 'app/**'
              - 'Gemfile.lock'
            frontend:
              - 'frontend/**'
              - 'pnpm-lock.yaml'

  backend-test:
    needs: check-diff
    if: needs.check-diff.outputs.backend_changed == 'true'
    runs-on: ubuntu-latest
    # ...

  frontend-test:
    needs: check-diff
    if: needs.check-diff.outputs.frontend_changed == 'true'
    runs-on: ubuntu-latest
    # ...
```

「入口で 1 回だけ差分を判定し、その結果を `outputs` で各ジョブの `if` に配る」という形にしておくと、判定ロジックが一箇所にまとまってスッキリします。`Gemfile.lock` が変わったときだけ依存セットアップを走らせる、といったきめ細かい制御もできます。

:::message alert
`if` でスキップされたジョブを **required status check（マージ必須チェック）に指定している**場合は注意が必要です。スキップされたジョブは "skipped" 扱いになり、required にしているとマージできなくなることがあります。スキップされうるジョブの扱いは、ブランチ保護の設定とセットで考えてください。
:::

### 古い実行はキャンセルする

PR に立て続けに push すると、古いコミットに対する CI がまだ走っているのに、新しい CI が積まれていきます。古いほうはもう結果が要らないので、`concurrency` でキャンセルしましょう。

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

`group` を「ワークフロー名 × ブランチ」にしておくと、同じブランチへの新しい push が来たときに、進行中の古い実行が自動でキャンセルされます。これは時間短縮というより**ランナー時間（コスト）の節約**ですが、混雑時にランナーの空き待ちが減るので、結果的に最新コミットの CI が早く回り始めます。

### ラベルやドラフトで実行自体を制御する

「WIP の draft PR では重い CI を回したくない」「レビュー準備ができたものだけ回したい」といった、もう一段上のゲートを入れる手もあります。ラベルで CI の発火を制御する方法は別記事に書いたので、興味があればどうぞ。

- [特定のラベルが付いたPRだけCIを走らせてGitHub Actionsのコストを削減する](https://zenn.dev/mandenaren/articles/ci_gate_by_pr_label)

## 4. ランナーを使い分ける

すべてのジョブを同じランナーで回す必要はありません。**処理の性質に合わせてランナーを選ぶ**と、速度とコストのバランスが取れます。

### 重い処理だけ強いランナーに載せる

GitHub Actions には、コア数を増やした larger runner があります（`ubuntu-latest` の 2 コアに対し、8 コア・16 コア・32 コアなど）。これらは**従量課金の単価が上がる**ので、全ジョブに使うとコストが膨らみます。

そこで、**並列テストのようにコアを使い切れる重いジョブだけを大きいランナーに載せ**、軽い Lint や型チェックは標準ランナーに置く、という使い分けをします。`parallel_tests` のようなプロセス並列はコア数に比例して速くなるので、大きいランナーの恩恵をフルに受けられます。

さらに踏み込むと、**変更範囲に応じてランナーのサイズも変える**こともできます。たとえば「特定のモジュールしか触っていない PR は、テスト対象も少ないので 8 コアで十分。全体に影響する変更のときだけ 32 コア」といった具合です。

```yaml
test:
  # 変更が局所的なら小さいランナー、そうでなければ大きいランナー
  runs-on: ${{ needs.check-diff.outputs.narrow_change == 'true'
    && 'ubuntu-latest-8-cores'
    || 'ubuntu-latest-32-cores' }}
```

「常に最大で回す」のではなく「必要なときだけ最大」にするのが、速度とコストの両取りのコツです。

### CPU アーキテクチャ（ARM / x86）を選ぶ

GitHub Actions には ARM 版ランナーがあり、x86 より**単価が安く、ワークロードによっては速い**ことがあります。基本は ARM に寄せるとコスト効率が良いです。

ただし**何でも ARM が速いわけではない**点に注意が必要です。実際に運用してみると、**DB に強く依存する処理は x86 のほうが速い**ケースに出くわします。たとえば PostgreSQL は ARM 環境での最適化が（少なくとも一時期は）x86 ほど枯れておらず、DB アクセスの多いテストを ARM で回すと逆に遅くなることがありました。

そこで、

- **DB 依存の重いジョブ（統合テスト等）** → x86 ランナー
- **DB に触らない静的解析・Lint・型チェック** → ARM ランナー

のように振り分けると、全体として速くて安い構成になります。「ARM が安いから全部 ARM」と決め打ちせず、**ジョブごとに実測して選ぶ**のがポイントです。

## 5. 個々のジョブ自体を速くする

並列化やスキップで「全体の構造」を最適化したら、最後は「個々のジョブの中身」を速くします。

### テスト用 DB をメモリに載せる

テストは大量に DB へ読み書きするので、**DB のディスク I/O がボトルネック**になりがちです。CI のテスト用 DB は実行が終われば捨てるものなので、永続性を捨てて速度に全振りできます。

GitHub Actions の service container で、データディレクトリを **tmpfs（メモリ上のファイルシステム）にマウント**すると、ディスク I/O が消えて目に見えて速くなります。

```yaml
services:
  mysql:
    image: mysql:8.0
    options: >-
      --mount type=tmpfs,destination=/var/lib/mysql
      --health-cmd="mysqladmin ping"
      --health-interval=5s
      --health-timeout=5s
      --health-retries=3
```

PostgreSQL なら、初期化時に `fsync` を切る（`--nosync` 相当）と速くなります。

```yaml
services:
  postgres:
    image: postgres:15
    env:
      POSTGRES_INITDB_ARGS: "--nosync"
```

いずれも「クラッシュしてもデータが飛んでいい」前提だからこそできる割り切りで、**本番では絶対にやってはいけない**設定です。使い捨ての CI 用 DB に限った高速化テクニックです。

### テストのセットアップを使い回す（before_all / let_it_be）

最初の「まず計測する」で `test-prof` を回した結果、「同じデータを example ごとに毎回作り直していて遅い」と分かったら、`before_all` / `let_it_be` の出番です。

通常の `let` や `before` は **example ごとに毎回実行**されるので、共通の親データ（ユーザー、組織、マスタデータなど）を全 example で作り直していると、その分だけ無駄に DB へ書き込みます。

```ruby
# Before: example ごとに毎回 user を作り直す（遅い）
RSpec.describe SomeService do
  let(:user) { create(:user) }

  it "..." do # ここで user 生成
  end

  it "..." do # ここでも user 生成
  end
end
```

`let_it_be` を使うと、**そのブロック内で 1 回だけ**データを作り、各 example で使い回せます。

```ruby
require "test_prof/recipes/rspec/let_it_be"

RSpec.describe SomeService do
  let_it_be(:user) { create(:user) } # describe 全体で 1 回だけ生成

  it "..." do # 生成済みの user を使う
  end

  it "..." do # 同上
  end
end
```

同様に、副作用を伴うセットアップ処理を 1 回だけ実行したいときは `before_all` を使います。

```ruby
before_all do
  # この describe/context で 1 回だけ走る重いセットアップ
end
```

:::message
`let_it_be` で使い回すデータは、example 間で**状態が共有される**点に注意です。あるテストでレコードを更新すると、後続のテストにも影響します。「テスト内で変更しない、参照だけの親データ」に使うのが基本です。変更が前提のデータは従来どおり `let` / `create` で都度作るほうが安全です。`test-prof` で「作りすぎ」が見えた重い factory から、影響範囲を見極めつつ個別に置き換えていくのがおすすめです。
:::

### テスト後の DB 掃除を ROLLBACK にする

各テストの後始末（作ったレコードの削除）の方式も、速度に効きます。よくある [`database_rewinder`](https://github.com/amatsuda/database_rewinder) や `DatabaseCleaner` の `deletion` ストラテジは、**テストで触れたテーブルを `DELETE` 文で 1 行ずつ消して**きれいにします。これは確実ですが、テストのたびに削除 SQL が大量に走るぶん遅くなります。

代わりに **トランザクションでくるんで `ROLLBACK` する**方式にすると、**削除 SQL がそもそも不要**になります。各 example の頭でトランザクションを開始し、終わったらコミットせずにロールバックするだけ。書き込んだデータは「無かったこと」になるので、明示的に消す必要がありません。

Rails なら RSpec の `use_transactional_fixtures`（= `use_transactional_tests`）を有効にするのが一番手軽です。

```ruby
RSpec.configure do |config|
  # 各 example をトランザクションで囲み、終了時に ROLLBACK する
  config.use_transactional_fixtures = true
end
```

`DatabaseCleaner` を使っているなら、`deletion` / `truncation` ストラテジから `transaction` ストラテジに変えるのと同じ発想です。

```ruby
config.before(:each) { DatabaseCleaner.strategy = :transaction }
```

`DELETE` を都度発行する方式から `ROLLBACK` 方式に変えるだけで、DB アクセスの多いテストスイートはまとまった時間が削れます。

:::message alert
`ROLLBACK` 方式には弱点もあります。**別コネクション（別スレッド／別プロセス）からはロールバック前のデータが見えない**ため、ブラウザを別プロセスで動かす **system spec（Capybara + 実ブラウザ）では使えません**。その手のテストだけは `truncation` / `deletion` に切り替える、という併用が定番です。「速いけど制約のある ROLLBACK を基本にしつつ、必要なところだけ DELETE/TRUNCATE」と使い分けるのが落としどころです。
:::

### ランタイムの実行を速くする

言語ランタイム側のスイッチで、テストやビルドそのものを速くできることもあります。

Ruby 3.3+ なら **YJIT**（JIT コンパイラ）を有効にすると、テスト実行やアセットのプリコンパイルが速くなります。

```yaml
env:
  RUBY_YJIT_ENABLE: "1"
```

Node 側では、大きめのテスト・ビルドで**ヒープ不足（out of memory）で落ちて、リトライで時間を溶かす**ことがあります。これはヒープ上限を引き上げておくと安定します。

```yaml
env:
  NODE_OPTIONS: "--max-old-space-size=8192"
```

これは「速くする」というより「**落ちて再実行になるのを防ぐ**」工夫ですが、CI の体感時間（＝緑になるまでの実時間）には地味に効きます。失敗 → 再実行のサイクルは、純粋な実行時間以上に開発のリズムを壊すので、安定性も立派な「時間短縮」です。

### ジョブの依存関係（needs）を見直す

最後に地味だけど効くのが、`needs` の整理です。GitHub Actions は `needs` で依存関係を組んだジョブを、依存が解決した順に並列実行します。ここで**本来並列にできるジョブを、無駄に直列にしていないか**を見直します。

```yaml
# 悪い例: static-analysis が test の完了を待つ必要はないのに直列になっている
test:
  needs: setup
static-analysis:
  needs: test        # ← test を待つ理由がないなら setup に変えるべき
```

```yaml
# 良い例: setup さえ終われば test と static-analysis は同時に走れる
test:
  needs: setup
static-analysis:
  needs: setup
```

依存グラフを「セットアップ → あとは可能な限り横並び」の形に近づけると、クリティカルパス（一番長い依存の鎖）が短くなって、全体の実時間が縮みます。CI が遅いと感じたら、一度ワークフローの依存グラフを図に起こしてみると、不要な直列が見つかることがあります。

## 番外編：落ちる CI を未然に防ぐ（lefthook）

ここまでは「CI そのものを速くする」話でしたが、忘れがちなのが **CI の往復回数を減らす**という視点です。

考えてみると、CI が一番ムダな時間を生むのは「**lint や format の崩れ、型エラーといった、手元で一瞬で分かるミスで CI が落ちる**」ときです。

1. push する
2. 10 分待つ
3. lint で落ちる
4. 直して push し直す
5. また 10 分待つ……

この往復は、CI 1 回ぶんの実行時間がまるごと無駄になっているうえに、開発のリズムも切られます。**どれだけ CI を速くしても、落ちる CI を 2 回回すより、落ちない 1 回で済ませるほうが速い**わけです。

そこで、**手元の git hook で軽いチェックを先に回し、落ちる変更をそもそも push させない**ようにします。git hook 管理には [lefthook](https://github.com/evilmartians/lefthook) が手軽です。Go 製で起動が速く、言語を問わず使え、複数コマンドを**並列実行**できるので、hook 自体が遅くなりにくいのが利点です。

リポジトリ直下に `lefthook.yml` を置きます。

```yaml
pre-commit:
  parallel: true
  commands:
    rubocop:
      glob: "*.rb"
      run: bundle exec rubocop --force-exclusion {staged_files}
    eslint:
      glob: "*.{js,ts,tsx}"
      run: pnpm eslint {staged_files}

pre-push:
  parallel: true
  commands:
    tsc:
      run: pnpm tsc --noEmit
```

ポイントを 3 つ。

- **`{staged_files}` で差分だけを対象にする**: 変更したファイルにだけ lint をかけるので、hook が一瞬で終わります。リポジトリ全体に lint をかけると遅くて、結局みんな `--no-verify` で素通りするようになります。**hook は速さが命**です。
- **重さで pre-commit / pre-push を使い分ける**: format や lint のように一瞬で終わるものは `pre-commit`、型チェックのように少し重いものは push 直前の `pre-push` に置く。commit のたびに重い処理が走るとストレスになるので、コミットは軽く保ちます。
- **`parallel: true` で同時実行**: rubocop と eslint のように独立したチェックは並列で回して、待ち時間を最小化します。

### あくまで CI の代わりではなく「前さばき」

注意点として、**lefthook は CI を置き換えるものではありません**。

- ローカル hook は `--no-verify` で簡単にスキップできる（＝強制力がない）
- 各自の手元環境に依存するので、CI ほど信頼できない

なので「**手元で安いチェックを先に潰して、CI を落とす確率を下げる**」前さばきと位置づけ、**最終的なゲートは CI に置く**のが正解です。テストのフル実行のような重い検証は CI に任せ、lefthook には「CI を落とすまでもない初歩的なミス」を引っかける役割を持たせます。

このすみ分けにすると、「手元で弾けるものは手元で（速い・CI を消費しない）」「ちゃんとした検証は CI で（信頼できる）」と、フィードバックが二段階になって、トータルの待ち時間が縮みます。

## 20% 速くすると、どれくらい効くのか（概算）

「で、結局やる価値あるの？」を判断するために、ざっくり試算してみます。**仮に CI を 20% 短縮できたら**、時間とお金がどれくらい浮くのか。あくまでオーダー感をつかむための概算で、数字は各チームの実態に置き換えてください。

### 前提（例）

| 項目 | 値 |
| --- | --- |
| 開発者 | 10 人 |
| 1 日の CI 実行回数（push 単位） | 50 回 |
| 営業日 | 月 20 日 → **月 1,000 回** |
| CI 1 回の wall-clock（緑になるまで） | 20 分 → **16 分**（▲4 分） |
| CI 1 回の課金マシン時間（全ジョブ合算） | 50 分 → **40 分**（▲10 分） |

wall-clock（実時間）と課金マシン時間を分けているのがポイントです。CI は複数ジョブが並列で走るので、**「緑になるまでの 20 分」と「課金される合計マシン時間」は別物**で、後者のほうが長くなります（並列ジョブの分だけ合算されるため）。

### 時間の削減

**人の待ち時間（wall-clock ベース）**

- 1 回あたり 4 分短縮 × 月 1,000 回 = **月 4,000 分 ≒ 約 67 時間**
- 開発者が CI 完了を実際に待っている割合を仮に半分とすると、**月 ~33 時間**ぶんの「待ち」が消える計算
- これは「マージまでのリードタイム短縮」「コンテキストスイッチの削減」として効いてきます。エンジニアの人件費を時給 5,000 円とすれば、待ち時間 33 時間 ≒ **月 16 万円相当**の機会損失が浮くイメージ

### コストの削減（GitHub Actions の課金）

GitHub Actions は**課金マシン時間（全ジョブの合計分数）**で課金されます。なので、お金の削減は wall-clock ではなく**マシン時間の削減ぶん**で見ます。

- 削減されるマシン時間 = 10 分/回 × 月 1,000 回 = **月 10,000 分**
- 標準 Linux ランナー（1 分あたり **約 $0.008** とする）の場合
  - **月 $80 ≒ 年 $960**（約 **月 1.2 万円 ≒ 年 14.4 万円**）
- larger runner 中心（仮に単価 4 倍の **約 $0.032/分**）の場合
  - **月 $320 ≒ 年 $3,840**（約 **月 4.8 万円 ≒ 年 57.6 万円**）

| ランナー | 単価（概算） | 月の削減 | 年の削減 |
| --- | --- | --- | --- |
| 標準 Linux | $0.008/分 | $80（約 1.2 万円） | $960（約 14.4 万円） |
| larger runner（例: 8 コア） | $0.032/分 | $320（約 4.8 万円） | $3,840（約 57.6 万円） |

:::message
ランナー単価はプラン・時期・ランナーサイズで変わります（2026 年にも価格改定が入っています）。ここでは広く知られた目安として標準 Linux ≒ $0.008/分、為替は 1 ドル ≒ 150 円として円換算しています。**自分の請求ページの実単価と最新レートで計算し直す**のが正確です。
:::

### 注意：その「20% 短縮」はどっちの 20%？

試算でいちばん大事なのは、**「CI 時間 20% 短縮」には 2 種類ある**という点です。

- **wall-clock（緑になるまでの実時間）の短縮** → 人の待ち時間・リードタイムに効く
- **課金マシン時間（全ジョブ合算）の短縮** → お金に効く

施策によって、効く先が違います。

- **キャッシュ・スキップ・重複キャンセル**は、wall-clock も課金マシン時間も**両方**減らせる（やった処理がまるごと消えるため）。コスト削減の本命
- **並列化（シャーディング・larger runner）**は、wall-clock は縮むが、**課金マシン時間はむしろ増える**ことがある（ジョブを増やす／強いマシンを使うため）。これは「お金で時間を買う」施策

なので「コストを下げたい」なら、まず**そもそも走らせない系（キャッシュ・スキップ）**から手を付けるのが効率的です。並列化は「人の待ち時間は減るが、請求額は必ずしも減らない（むしろ増えることもある）」と理解したうえで、リードタイム短縮の価値と天秤にかけて選びます。

## まとめ

CI 高速化は「これ一発で速くなる」という銀の弾丸があるわけではなく、**小さい工夫の積み重ね**です。今回紹介した施策を、効果と導入コストの観点でざっくり整理すると次のようになります。

| 系統 | 施策 | ねらい |
| --- | --- | --- |
| キャッシュ | 依存 / Lint / Docker レイヤー | インストール・ビルドの再実行を省く |
| 並列化 | parallel_tests + 実行時間ログ / matrix シャーディング | テストを分散して縮める |
| 動かさない | paths-filter / concurrency / ラベルゲート | そもそも走らせない |
| ランナー | larger runner の出し分け / ARM・x86 の選択 | 必要なときだけ強いマシン |
| ジョブ高速化 | tmpfs DB / ROLLBACK 掃除 / let_it_be / YJIT / needs 整理 | 個々の処理とクリティカルパスを短縮 |
| 往復を減らす | lefthook で手元チェック | 落ちる CI を未然に防ぎ、CI の再実行を減らす |

おすすめの始め方は、

1. まず**計測**して、どのジョブ・どのテストが遅いのかボトルネックを特定する（`test-prof` など）
2. **依存キャッシュ**を入れる（一番ラクで効果が出やすい）
3. **変更パスでのスキップ**と**concurrency キャンセル**を入れる（コスパが良い）
4. テストが重いなら、計測で見つけた遅い相手を**まず直す／使い回す**（`let_it_be`・ROLLBACK 掃除など）
5. それでも遅ければ**テストの並列化**に手を付ける（一番効くが手間もかかる）

の順です。これと並行して、**lefthook で手元チェックを入れ、「落ちる CI」を未然に防ぐ**のも、いつ入れても効くおすすめの一手です。そして**何より、最初に計測する**のを忘れずに。CI の実行時間は、放っておくと伸びる一方ですが、こうした工夫を仕込んでおくと、プロジェクトが大きくなっても「待ち時間で開発が止まる」状態を避けられます。請求書とにらめっこする前に、まずは一番上のキャッシュから試してみてください。
